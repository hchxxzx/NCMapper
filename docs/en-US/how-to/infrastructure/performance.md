# Performance and Best Practices

## Overview

NCMapper’s dual-engine architecture (source generator + runtime expression trees) exhibits distinct performance characteristics across different scenarios. This article covers comparative performance data, optimization recommendations, common misuse patterns, and best practices—helping you achieve optimal performance in hot-path scenarios.

Core APIs: `Mapper.Map<T,S>(src)` / `src.MapToXxxDto()` / `Mapper.MapList<T,S>(srcs)` / `Mapper.DeepCopy<T>(src)` / `Mapper.ClearCache()`

---

## 1. Dual-Engine Performance Comparison

NCMapper provides two mapping execution paths, automatically selected based on whether the DTO is annotated with `[MapFrom]`:

> **Test Environment & Methodology**: The “Typical Performance” values on this page are derived from a full benchmark batch run on 2026-10-07 (net10.0): **Intel Xeon Silver 4314 @ 2.40GHz (2 sockets / 40 logical cores, CPU base frequency locked to cores 0–19), Ubuntu 24.04.5 LTS, BenchmarkDotNet 0.14.0** (5 process invocations × 15 iterations each, with 3 warmup iterations).  
> Performance numbers vary significantly across CPU models, OS versions, and .NET versions (real-world measurements on different machines may differ by 1–2× for identical scenarios). Values on this page are intended *only* to assess **relative differences and magnitude between execution paths**, not as absolute cross-environment performance guarantees. Complete cross-framework, full-scenario benchmark data is available in [Performance Optimization Mechanisms](../../explanation/performance.md) §14.6.

| Invocation Style | Execution Path | Typical Performance | First-Call Overhead |
|---|---|---|---|
| `entity.MapToUserDto()` | Source-generator extension method — direct zero-delegate call | ~13–27 ns/op | None (generated at compile time) |
| `Mapper.Map<UserEntity, UserDto>(entity)` | Delegate registry lookup → source-generated code | ~17–29 ns/op | None |
| `Mapper.Map<T, U>(src)` (unannotated with `[MapFrom]`) | Runtime expression-tree compilation; cached after first compilation | ~19–38 ns/op | Yes (~1–5 ms for first compilation) |

- The source-generator path delivers optimal performance in hot-path scenarios — zero delegate lookups, fully JIT-inlinable.

## 2. Deep Copy Strategy Performance

Deep copy strategies are defined by the `DeepCopyStrategy` enum, which has three values. The default is `Fast`, each mapping to a specific provider:

**Execution Logic (Priority Order)**: `Mapper.DeepCopy<T>` does *not* directly route to a strategy-specific provider. Instead, it performs two-layer automatic routing, starting with source-generated delegates:

1. **Layer 1 · Source Generator (Optimal)**: When the type is annotated with `[MapFrom]`, the source generator registers a dedicated deep-copy delegate at compile time. `Mapper.DeepCopy` invokes it directly (~179 ns/op under net10.0 Linux), completely bypassing `DeepCopyProviderBase.Current` and `DeepCopyStrategy` configuration.
2. **Layer 2 · Runtime Strategy**: If no source-generated delegate exists, the call falls back to `DeepCopyProviderBase.Current` (defaulting to `Fast`).

Thus, “default = Fast” holds *only* for types **not annotated with `[MapFrom]`**.

| Enum Value | Corresponding Provider Type | Semantics |
| --- | --- | --- |
| `DeepCopyStrategy.Fast` | `FastDeepCopyProvider` | Default (for unannotated types); supports cyclic references; Acyclic fast path with zero-cycle-detection overhead |
| `DeepCopyStrategy.ExpressionTree` | `ExpressionTreeDeepCopyProvider` | Full cyclic-reference detection |
| `DeepCopyStrategy.Json` | `JsonDeepCopyProvider` | JSON serialization round-trip fallback; *does not support* cyclic references |

| Strategy | Typical Performance | Cyclic References | Applicable Scenarios |
|---|---|---|---|
| `FastDeepCopyProvider` (default) | Acyclic: ~401 ns (fast path); Cyclic: delegates to base-class full detection (any cycle length) | Supported (Acyclic zero-detection + Cyclic full detection) | Conditional dispatch — preferred default; *does not preserve DAG shared references* |
| `ExpressionTreeDeepCopyProvider` | ~409 ns | Any cycle length | Required when DAG shared references must be preserved |
| `JsonDeepCopyProvider` | ~1697 ns | Not supported | Compatibility fallback (serialization + deserialization) |

> ⚠ **DAG Shared References**: In the `Fast` path, Acyclic-DAG shared references are copied independently at each occurrence (“per-location independent copy”). To preserve sharing semantics, use `ExpressionTreeDeepCopyProvider`.

Strategies can also be configured via the `NCMapperOptions.DeepCopyStrategy` property or the `DeepCopyStrategy` key in `appsettings.json` (string values: `Fast`/`ExpressionTree`/`Json`; default: `Fast`). Direct assignment is equivalent. Runnable examples (with `try`/`finally` restoration):

**Key Points**:

- Strategy switching is global and affects all subsequent `Mapper.DeepCopy` calls.
- Always restore the original strategy after temporary changes (typical `try`/`finally` pattern).
- `FastDeepCopyProvider` is the default strategy (applies *only* to types **not annotated with `[MapFrom]`**) and performs three-value classification of type graphs (Acyclic/Cyclic/Unknown) for conditional dispatch:
  - **Acyclic**: Zero-detection fast path (~401 ns); cycle buffer serves only as false-negative fallback (max cycle length ≤ 8), rarely triggered in practice.
  - **Cyclic/Unknown**: Delegates to base-class full detection (using `CycleCache` + record placeholders; handles arbitrary cycle lengths).
  - **`Fast` now fully supports cyclic references** — no need to switch to `ExpressionTree` solely for self-references or cycles. The sole semantic difference lies in DAG shared-reference handling (see below).
- `ExpressionTreeDeepCopyProvider` provides full cyclic-reference detection (any cycle length) and **preserves DAG shared references**; `Fast`’s Acyclic path prioritizes speed by copying shared nodes independently at each location.
- Types annotated with `[MapFrom]` use **source-generated deep copy** (compile-time generated, bypassing all above providers), typically ~179 ns/op (net10.0 Linux), making it the **fastest path overall** (note: it is *not* part of the `DeepCopyStrategy` enum — it is Layer 1, highest-priority, and cannot be switched via `DeepCopyProviderBase.Current`).
- Recursion depth limits are controlled via `DeepCopyContext.MaxRecursionDepth` to prevent stack overflow.

## 3. List and Collection Mapping Performance

| Operation | Typical Performance (1000 items) | Notes |
|---|---|---|
| `Mapper.MapList<T, U>(list)` | ~24.6 μs | Batch-optimized internally |
| Individual `Mapper.Map<T, U>(item)` | ~25 μs | Same order of magnitude as `MapList` |
| Source-generator `list.MapToXxxDtoList()` | ~24.6 μs | Zero-delegate batch mapping |

**Key Points**:

- `MapList` and individual `Map` calls perform at the same scale (~25 μs per 1000 items, Linux 20261007 benchmark), but `MapList` avoids per-item delegate lookups.
- Source-generator list extension methods (`MapToXxxDtoList()`) eliminate delegate lookups entirely.
- Collection types are auto-detected (14 types supported: `List`, `Array`, `HashSet`, `Dictionary`, etc.) — no manual conversion required.
- For high-frequency bulk operations where target objects can be reused, prefer `MapListInto` to populate pre-allocated arrays: zero allocations at the top level — see [MapListInto](../mapping/map-list-into.md).

**`MapListInto` Reuse Scenario Performance** (single-threaded = full benchmark on Linux 20261007; multi-threaded = real-world load test on 20260820):

- Single-thread throughput (100 items/call): ~0.48 μs/call (net8.0/net9.0/net10.0: 481/482/476 ns, NCMapper path), **5.1×–5.6× faster** than equivalent `MapList`.
- 16-thread scaling efficiency: 0.66–0.71 (net8.0/net9.0/net10.0: 0.660/0.701/0.710; metric: `TPS_16T / (TPS_1T × 16)`, 20260820 load test).
- Top-level zero allocations in reuse scenario (measured: 0 B / 0 Gen0 ×10000); nested reference properties still allocate new sub-objects per iteration.

## 4. Compose and Pipeline Overhead

| Operation | Typical Overhead | Notes |
|---|---|---|
| Compose (two sources) | ~30–50 ns/op | Multi-source composition; slightly slower than single-source `Map` |
| Compose (three sources) | ~40–60 ns/op | Three-source composition |
| PostMap (single layer) | ~5–10 ns/op | Outermost callback in onion model |
| PostMap (three layers) | ~15–30 ns/op | Three-layer nested callbacks |

**Key Points**:

- `Compose` overhead stems mainly from multi-source property resolution — marginally slower than single-source `Map`, but far more efficient than manual concatenation.
- `PostMap` callbacks execute in reverse registration order (onion model); overhead increases linearly with nesting depth.
- `Mapper.Pipeline.Clear()` clears all registered `PostMap` callbacks and sets the read-only property `IsEnabled` to `false` — subsequent mappings skip all `PostMap` logic. To re-enable, re-register via `AddPostMap` (registration automatically enables the pipeline; source anchor: `MapPipeline.cs`: lines 133 & 158).

## 5. Cold Start and Caching

“Cold start” in NCMapper refers to the initialization overhead incurred on the *first* mapping call for a given type pair:

| Scenario | Cold-Start Overhead | Subsequent Calls |
|---|---|---|
| Annotated with `[MapFrom]` (source-generator path) | ~0 ns (generated at compile time) | ~17–29 ns |
| Unannotated (runtime compilation) | ~1–5 ms (expression-tree compilation) | ~19–38 ns |

[!code-csharp[Cold-start latency after ClearCache (including expression-tree compilation)](~/samples/NCMapper.Samples/06-Infrastructure/PerformanceScenarios.cs#Core_Perf_ColdStartAfterClear)]

**Key Points**:

- `Mapper.ClearCache()` clears all mapping caches *and* `MaskProvider` overrides; subsequent first calls require recompilation.
- Avoid calling `ClearCache()` at runtime in production (triggers cold-start penalty on next mapping).
- In testing, `ClearCache()` is useful for verifying cold-start behavior.

## 6. AOT / NativeAOT Compatibility

NCMapper is designed with AOT scenarios in mind, though certain reflection-based capabilities are unavailable under NativeAOT.

**AOT-Friendly Components**:

- Source-generator path (`[MapFrom]`-generated static mapping methods) is fully AOT-compatible — zero runtime reflection.
- Attributes such as `[MapFrom]`, `[MapProperty]`, and `[MapIgnore]` are analyzed at compile time.
- Mapping delegates are generated at compile time by the source generator (zero reflection, no dependency on `[DynamicallyAccessedMembers]`); trimming preserves all required members.

**Components Unavailable Under AOT**:

| API | Reason | Mitigation |
|---|---|---|
| `Mapper.Validate(params Assembly[])` | Uses reflection to scan assemblies and types (`[RequiresDynamicCode]` / `[RequiresUnreferencedCode]`) | Rely exclusively on the source-generator path (`[MapFrom]`) in production; avoid runtime reflection scanning. |
| `JsonSerializerBase` reflection-based serialization | Annotated with `[RequiresDynamicCode]` / `[RequiresUnreferencedCode]` | Use source-generated `JsonSerializerContext` instead. |
| ORM projection extensions (`AsDto` → `ToList`, etc.) | `BuildProjection` uses `MakeGenericMethod` (`[RequiresDynamicCode]` / `[RequiresUnreferencedCode]`); no source-generator alternative exists | Projection paths are unavailable under AOT; fall back to memory-based `MapList`/`Compose` paths *if* annotated with `[MapFrom]`. |

**Key Points**:

- In production, annotate *all* DTOs with `[MapFrom]` to ensure mappings always use the source-generator path (zero runtime reflection).
- Under NativeAOT publishing, types *not* annotated with `[MapFrom]` will fail at runtime during first mapping due to reflection unavailability — full annotation is mandatory.
- `Validate(params Assembly[])` is intended *only* for development-time validation; under NativeAOT, rely on the source-generator path to guarantee availability.

## Common Misuses

### Misuse 1: Measuring Cold Start with Stopwatch Without Warmup

```csharp
// ❌ Misuse: First call includes expression-tree compilation overhead → distorted measurement
Mapper.ClearCache();
var sw = Stopwatch.StartNew();
var dto = Mapper.Map<UserEntity, UserDto>(entity);  // Includes ~1–5 ms compilation overhead
sw.Stop();
Console.WriteLine($"{sw.Elapsed.TotalMicroseconds:F2}μs");  // Result inflated by >100×

// ✅ Correct: Pre-warm (trigger compilation + caching), then measure
Mapper.ClearCache();
Mapper.Map<UserEntity, UserDto>(entity);  // Warmup: triggers compilation
var sw = Stopwatch.StartNew();
for (int i = 0; i < 1000; i++)
    Mapper.Map<UserEntity, UserDto>(entity);  // Hot-path measurement
sw.Stop();
Console.WriteLine($"{sw.Elapsed.TotalMicroseconds / 1000:F2}μs/op");
```

> NCMAP099 is an internal diagnostic code emitted by the source generator to report exceptions during generation. If NCMAP099-related errors appear in benchmarks, the source generator likely encountered an unsupported type structure at compile time — verify correctness of `[MapFrom]` annotations on your DTOs.

### Anti-pattern 2: GC Interference Causing Data Distortion

```csharp
// ❌ Anti-pattern: Uncontrolled GC — GC pauses cause measurement jitter
var sw = Stopwatch.StartNew();
for (int i = 0; i < 10000; i++)
    Mapper.Map<UserEntity, UserDto>(entity);
sw.Stop();
// If GC is triggered during the loop, results may be inflated 10–100×.

// ✅ Correct: Force GC before measurement and avoid allocations during measurement
GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();

var sw = Stopwatch.StartNew();
for (int i = 0; i < 10000; i++)
    Mapper.Map<UserEntity, UserDto>(entity);  // Mapping itself allocates nothing
sw.Stop();
```

### Anti-pattern 3: Calling `ClearCache` at Runtime in Production

```csharp
// ❌ Anti-pattern: Calling `ClearCache` inside web request handling
app.MapGet("/users/{id}", (int id) =>
{
    Mapper.ClearCache();  // Cache cleared on *every* request!
    return Mapper.Map<UserEntity, UserDto>(userService.Get(id));
});
// Consequence: Every request suffers cold-start penalty — performance degrades 100× or more.

// ✅ Correct: Use `ClearCache` only at application startup or in tests.
// In production, mapping caches are managed automatically — manual clearing is unnecessary.
```

### Anti-pattern 4: Omitting `[MapFrom]`, Forcing Runtime Expression Compilation

```csharp
// ❌ Anti-pattern: DTO lacks `[MapFrom]`, triggering runtime expression tree compilation
public class UserDto { ... }  // No [MapFrom] attribute
var dto = Mapper.Map<UserEntity, UserDto>(entity);  // ~19–38 ns per call; first call incurs ~1–5 ms compilation overhead
// NCMAP019 Info: UserDto does not declare [MapFrom] (runtime mapping remains functional, but Source Generator optimization path is unavailable)

// ✅ Correct: Annotate with `[MapFrom]` to enable compile-time code generation by the source generator
[MapFrom(typeof(UserEntity))]
public class UserDto { ... }
var dto = Mapper.Map<UserEntity, UserDto>(entity);  // ~17–29 ns per call; zero compilation overhead
```

### Anti-pattern 6: Leaving Trace Enabled Long-Term in Production

```csharp
// ❌ Anti-pattern: Enabling `MapTracer` in production
MapTracer.GloballyEnabled = true;  // Performance overhead ~15–20%
// Detailed diagnostic logs emitted on every mapping — severely impacts throughput

// ✅ Correct: Enable `MapTracer` only temporarily during debugging or troubleshooting
if (env.IsDevelopment())
{
    MapTracer.GloballyEnabled = true;
}
// Keep it disabled in production
```

## Best Practices

1. **Always annotate with `[MapFrom]`**: Enables source generator to emit compile-time code, eliminating runtime compilation overhead (as warned by diagnostic NCMAP019).
2. **Prefer extension methods on hot paths**: `entity.MapToUserDto()` avoids one dictionary lookup compared to `Mapper.Map<>()`.
3. **Use `MapList` for list mappings**: `MapList` processes items in bulk internally — significantly faster than mapping individual items in a loop.
4. **Choose deep copy strategy wisely**:  
   - Use `Fast` (default) for cyclic graphs with ≤ 8 nodes.  
   - Use `ExpressionTree` for graphs with > 8 nodes or when DAG sharing preservation is required.
5. **Disable `MapTracer` in production**: `MapTracer.GloballyEnabled` imposes ~15–20% runtime overhead.
6. **Use correct `PostMap` scope**: `PostMap` registrations are process-global and intended for cross-cutting concerns (e.g., auditing, logging, formatting). Register them once at application startup and retain them long-term — do *not* call `Clear()` per mapping. For one-off custom transformations, use the `Action<T>` overload of `Mapper.Map(src, action)` (cleanup is automatic per call). Only in controlled scopes like unit tests should you pair registration with explicit teardown (`Clear`).
7. **Avoid runtime `ClearCache` calls**: Reserve `ClearCache()` for startup or test scenarios only — production cache management is fully automatic.
8. **Warm up benchmarks**: Invoke the mapping operation once before timing to trigger compilation and avoid cold-start distortion.
9. **Control GC during benchmarking**: Call `GC.Collect()` before measurement to prevent GC pauses from skewing results.
10. **Restore deep copy strategy using `try/finally`**: When temporarily switching deep copy strategies, always restore the default strategy afterward.
